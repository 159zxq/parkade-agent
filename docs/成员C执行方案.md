## 2. 你要理解的三件事（10 分钟读完）

1. **RAG 是什么**：把规章切成小段（chunk）→ 用嵌入模型转成向量存起来 → 用户提问时把最相似的 3 段找出来（这一步叫检索）→ 大模型只根据这 3 段回答。你的工作就是保证"切得对、找得准"。
2. **chunk 是评测的最小单位**：每段有编号（如 `3.2-01`）。评测集里每条问题标注了"正确答案应该在哪几个 chunk"，评测脚本看这 3 段里有没有它——**有，这条就算命中**。所以切得好不好，直接决定命中率。
3. **费率数字纪律**：你写的所有价格数字，必须和 `common/rates.yaml` 一模一样。**建库前逐项对一遍**（A 会再验收一遍）。"解释"和"计算"数字打架是全场最丢分的 bug。

## 3. 语料怎么写（你的主要工作，W1 就开写）

**目录结构**（固定 7 章，文件 `kb/corpus/`）：

| 文件 | 章节 | 内容 |
|---|---|---|
| `01_总则.md` | 1 总则 | 停车场简介、开放时间 24h、管理方、总则条款 |
| `02_区域与车位.md` | 2 区域与车位 | A 地面 30 位 / B 地下一层 60 位 / C 地下二层 60 位、引导规则 |
| `03_费率与计费规则.md` | 3 费率与计费 | 3.1 计费单位与免费时段；3.2 分时段费率表；3.3 夜间价与封顶；3.4 跨天规则 |
| `04_月卡与优惠.md` | 4 月卡与优惠 | 三种车型月卡价、办理与退订、优惠说明 |
| `05_预约规则.md` | 5 预约规则 | 免费预约、保留至预约后 30 分钟、超时释放、冲突限制 |
| `06_场内须知.md` | 6 场内须知 | 限高限速、禁停区、收费标准公示、发票、突发情况处理 |
| `07_FAQ.md` | 7 常见问题 | 30 条一问一答（每条 2–4 句） |

**写作规范**：
- 每节标题带编号（`3.2 分时段费率标准`），正文里费率数字加粗；
- **每一节 = 未来 1 个或多个 chunk**，一节 200–400 字为宜（太长就拆小节）；
- 语言正式、条款化（"小型车在标准时段（07:00–22:00）按 3 元/30 分钟计收……"）；
- 写每条 FAQ 时，**顺手把 1–2 条评测 QA 写进 `eval_set.csv`**（见 §5）。

**用 AI 加速写作**（推荐用法）：

```
我在写停车场规章《费率与计费规则》第 3.2 节，请按条款口吻帮我扩写。
必须使用的数字（不许改动，不许新增费率）：
小型车标准价 3 元/30 分钟；中型车 5 元；大型车 8 元；
夜间（22:00–07:00）为标准价 50%；当日封顶：小 30 / 中 45 / 大 60 元。
要求：200–350 字；条款化；只写这一节；不要编造其他规则。
```

FAQ 批量生成：

```
根据以下已定规则，生成 10 条停车场常见问题 FAQ（每条问题+2–4 句答案），
覆盖：计费、月卡、预约、【某个薄弱点】。只用我给的事实，不知道的不要编。
【粘贴 03/04/05 章全文】
```

**AI 生成的语料必须逐条核对两件事**：①数字与 rates.yaml 一致；②没有无中生有的规则（AI 很爱编"会员积分""首小时免费"这类假条款——你写了它就会进入知识库，答辩问答翻车）。

## 4. 建库脚本 `kb/build_index.py`（W2，A 给示例你扩写）

- 流程：遍历 `kb/corpus/*.md` → 按 `##` 标题切块（200–400 字，相邻块开头重叠 1–2 句）→ 每块生成 `chunk_id`（章.节-序号）→ **分批（≤10 条）调 text-embedding-v3** → 写 Chroma（`kb/chroma_db/`，集合 `parking_rules`）。
- 命令行：`python kb/build_index.py --rebuild`（先清后建；不加参数=增量）。
- 验收：
  ```bash
  python kb/build_index.py --rebuild     # 打印 ingested N chunks
  python -c "from agent.rag import retrieve; print(retrieve('夜间收费什么价'))"
  # 返回的第 1 条应来自 03_费率…md，score 明显高于无关问题
  ```
- 常见坑：一次灌 150 条会报错（所以强制分批，碰到 400 错误就是没分批）；脚本要能重复跑（先清后建），失败可重跑，不要求"一次成功"。

## 5. 评测集 `kb/eval_set.csv`（※与语料同步写，不能后补）

列：`id,question,expected_chunk_ids,category,note`。示例：

```csv
id,question,expected_chunk_ids,category,note
Q001,小型车白天停车怎么收费？,3.2-01,费率,费率表核心条款
Q002,晚上十点以后便宜多少？,3.2-02|3.2-03,费率,夜间价50%
Q003,停车一天最多收多少钱？,3.3-01,费率,封顶
Q004,预约后最晚什么时候到？,5.1-02,预约,保留30分钟
Q005,月卡怎么办、多少钱？,4.1-01|4.1-02,月卡,办理+价格
Q006,停车场老板的手机号是多少？,—,域外,应拒答
```

要点：
- **每写完一节语料，立刻写 1–2 条 QA**（趁记忆新鲜，同时检查"这节写清楚了吗"）；
- 问题用口语（模拟真实用户），别抄原文标题——测的是检索不是复读；
- `expected_chunk_ids` 要**实际点开 chunk 编号填**，不许凭感觉；
- 分布：费率 20 / 预约 10 / 须知 10 / 月卡 10 / 多轮 5 / 域外 5 = 60 条；
- 域外条目的 expected 留空，评测脚本会单独处理（预期行为=拒答，不参与命中率分母）。

## 6. 评测脚本 `kb/eval_rag.py`（W2 搭好，W3 反复跑）

- 读 eval_set → 逐条 `retrieve(question, k=3)` → 判断 expected 中任一 chunk 是否出现在 top3 → 输出：
  - 总命中率、分类命中率、失败清单（每条：问题 + expected + 实际 top3 + 相似度）；
- 命令：`python kb/eval_rag.py --eval-set kb/eval_set.csv --k 3`
- **迭代方法**：命中率不够时，**先看失败清单再动手**——常见原因按顺位：
  1. 该知识点没写进语料（补语料）；
  2. 语料写法与口语问法差太远（在 FAQ 里补一条口语化版本）；
  3. chunk 切太碎/太长（调整切分，改 build_index 的切块规则后重建库）；
  4. 检索词本身太泛（给 AI 看失败清单找规律，但结论要你自己核对语料后确认）。
- A 会收敛你的评测报告进测试报告；**W3 末 ≥95% 是硬闸门**，到时若仍 <90%，A 会接手一起调，你转去补 B7 测试记录——这是提前说好的兜底，不是失败。
